## Models :--> 
A model in dbt is a SQL file that contains the logic for transforming raw/source data into clean, business-ready data.
dbt executes these SQL models and creates database objects such as tables, views, or incremental tables.
Models can also reference other models using {{ ref() }}, allowing dbt to automatically manage dependencies and execution order.

Model Name or Model File Name will be the object name in snowflake automatically. 


## Models Folder :--> 
All data transformation logic has to be in model folder. Under this folder we can create multiple SQL files. 
Ex: Customer.sql, product.sql and the transformation logic in sql files. 
When we execute dbt run command, dbt will take this SQL code and will create a table or view inside snowflake. 

((The models folder contains the SQL files that define how your data should be transformed.
Each model usually represents a table or view that dbt creates in the target database.
You write the transformation logic using SQL, and dbt handles execution, dependencies, and creation of the final objects.))
models = Where you write your data transformation/business logic.
Models are the core building blocks of a dbt project. They can be layered (e.g., staging → intermediate → marts) and dbt builds them in the correct dependency order using ref().

If we are creating additional folder under Models folder, then same thing we have to mentioned in the dbt_project.yml file as well with materialization option.

By mentioning materialization in model file, we can override the materialization provided in dbt_project.yml file. Since model has the higher precedence.


## Macros :--> 
A macro in dbt is a reusable block of Jinja + SQL logic. Its similar to sql functions.  
With the help of macros, we can avoid the repeating same SQL logic across multiple models and can have dynamic sql based on parameters. 

Macros are especially useful for common business logic, dynamic SQL generation, or operations where code can be re-use across multiple models. 

macros = Reusable functions/blocks of SQL logic in dbt.


## Macros Folder :--> 
The macros folder contains reusable SQL/Jinja code that you can use across multiple models.
Macros help you avoid writing the same logic repeatedly and make your dbt code cleaner and easier to maintain.
They can also be used to create dynamic SQL, such as generating column names or applying common transformations.


## DBT Models Use Case point : 

I created a Vendor model in dbt. The requirement was to take vendor data from the source layer, apply the required business transformations and cleansing, and create a standardized vendor dataset in the target/reporting layer.

## DBT Macros Use Case point :

1) Vendor Name → Uppercase
Created a macro to convert vendor names to uppercase:

		{{ to_upper('vendor_name') }}

## SQL JINJA syntax : 

		{% macro to_upper(column_name) %}

			UPPER({{ column_name }})

		{% endmacro %}

## Use in Model:

		SELECT
			{{ to_upper('vendor_name') }} AS vendor_name
		FROM {{ ref('stg_vendor') }}

2) Standardize Vendor Name
Create a macro to remove extra spaces and standardize vendor names:

		{{ clean_vendor_name('vendor_name') }}

## SQL JINJA syntax: 

		{% macro clean_vendor_name(column_name) %}

			UPPER(TRIM({{ column_name }}))

		{% endmacro %}

## Use in Model:

		SELECT
			{{ clean_vendor_name('vendor_name') }} AS vendor_name
		FROM {{ ref('stg_vendor') }}

3) Handle NULL Vendor Values
Create a reusable macro to replace NULL/blank vendor values with a standard value = 'UNKNOWN'

## SQL JINJA Syntax:

		{% macro handle_null_vendor(column_name) %}
	
			COALESCE(NULLIF(TRIM({{ column_name }}), ''), 'UNKNOWN')

		{% endmacro %}

## Use in Model:

		SELECT
			{{ handle_null_vendor('vendor_name') }} AS vendor_name
		FROM {{ ref('stg_vendor') }}


I created macros for repetitive vendor transformations like converting Vendor Name to uppercase, standardizing vendor names and and handling NULL values. Instead of repeating the same SQL across multiple models, I created reusable macros and called them wherever required.

## Source Freshness :--> Source freshness checks how recently the source data was updated, so we know whether the data is fresh enough for reporting.
In source.yml, we define thresholds such as warn_after and error_after. dbt checks the source data timestamp column against the current time. If the data is older than the threshold, dbt gives a warning or error.

dbt source freshness :--> this command runs a query against your Snowflake source table to check when its data was last loaded or updated. It does not update the source table or refresh the data. It only checks freshness and reports the result.

For example, if your Vendor table was last updated 30 hours ago and your error_after threshold is 24 hours, dbt reports an error-level freshness status

What it does in the database:--> 
	
	1. Reads the configured timestamp column (loaded_at_field).
	2. Finds the latest timestamp in the source table.
	3. Compares it with the configured warning/error thresholds.
	4. Reports whether the source data is fresh, stale, or missing.
	

how to configure a source freshness condition ?

Go to source.yml file from models folder --> define table details on which source freshness needs to be configured --> under config, mentioned the timestamp column for "loaded_at_field", because we need to mention for which column we need to check freshness for, and below that freshness warn_after / error_after and rest info.


Without configuring first, we cant use Source Freshness command. For configuration details, check source.yml from models folder. 

Once we ran the command, dbt source freshness : we can see if fresh data exist, then data freshness will get passed, else warning or error as we have set it up.

## Snapshots :--> Snapshots in dbt are used to track historical changes in records. Its commonly used to implement SCD Type 2.

Snapshot: Detects changes in source records and maintains historical versions.
dbt_valid_from : start date
dbt_valid_to : end date 


example :
customer changes their city from Pune to Mumbai.

CUSTOMER_ID	--	CITY	--	DBT_VALID_FROM	--	DBT_VALID_TO

   101			Pune		Jan 1					Jan 10
   101	        Mumbai		Jan 10					NULL

Instead of overwriting Pune with Mumbai, the snapshot preserves the old record and creates a new version.

There area 2 strategies of implementing snapshots:

	1) Timestamp Strategy :
		when data have columns like Insert_date, Update_date, last_modified_date etc. 

	2) Check Strategy :
		when source data has no timestamp columns, then DBT compares the columns for data change, and it finds any, it will create a snapshot. 
		
dbt snapshot :--> to run the snapshots

after making changes in data, we need to run dbt snapshot command, so changed data can be visible under snapshot table.

## JINJA :--> Jinja is used to generate dynamic SQL instead of writing repetitive, static SQL code. It supports variables, loops, conditions, and macros to make SQL reusable and flexible.
In jinja {{ }} is used to print variables or call functions, while {% %} is used for logic such as loops and conditions.

Main benefit: It reduces code duplication and helps build scalable, metadata-driven data pipelines.

dbt processes Jinja during compilation and generates the final SQL that runs against your data warehouse.

In SQL we can use If-Else statements, for loop, variables, but in JINJA we can use them, and this way we can make SQL code more dynamic.
SQL = Query Language, still using JINJA we can use programming laguage functions to SQL. 

SQL --> select * from emp; -- on db, it will directly, without mentioning database & schema.
JINJA --> select * from {{ ref('emp') }}
		{ ref('emp') }} ---> convert into sql as database.schema.emp 
		
In DBT we use Jinja SQL, the combination of both.


in snowflake :--> select 'Hello There' as msg;
in JINJA :--> select '{{"Hello there}}'

For more syntax and detailed notes for Jinja, visit snfk_dbt_retail --> models --> JINJA
